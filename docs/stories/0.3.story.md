## User Story

**Como** desenvolvedor do backend,
**Quero** que o Node.js use Redis para garantir idempotencia no processamento de webhooks do WhatsApp,
**Para que** mensagens duplicadas (enviadas multiplas vezes pela Meta) sejam descartadas antes de processar, evitando que o cliente receba mensagens repetidas.

## Escopo

### Padrao de Idempotencia SET NX

```typescript
// src/services/webhook-idempotency.ts
import { createHash } from 'crypto'
import { redis } from '../config/redis'

const WEBHOOK_TTL_SECONDS = 86400 // 24 horas

export async function isWebhookDuplicate(payload: object): Promise<boolean> {
  const hash = createHash('sha256')
    .update(JSON.stringify(payload))
    .digest('hex')

  const key = `webhook:processed:${hash}`

  // SET key value NX EX ttl
  // Retorna null se a chave JA existe (duplicata)
  // Retorna "OK" se a chave foi CRIADA (novo)
  const result = await redis.set(key, '1', 'NX', 'EX', WEBHOOK_TTL_SECONDS)

  return result === null // true = duplicata
}
```

### Rota de Webhook

```typescript
// src/routes/webhook.ts
app.post('/webhook/whatsapp', async (req, reply) => {
  // 1. Verificar assinatura Meta (HMAC-SHA256)
  verifyWebhookSignature(req)

  // 2. Checar idempotencia ANTES de enfileirar
  const isDuplicate = await isWebhookDuplicate(req.body)
  if (isDuplicate) {
    return reply.status(200).send({ status: 'duplicate_discarded' })
  }

  // 3. Enfileirar para processamento assíncrono
  await webhookQueue.add('process-webhook', req.body)

  return reply.status(200).send({ status: 'queued' })
})
```

## Dev Notes

### Por que SET NX e nao GET + SET?

`SET key value NX` e uma operacao atomica no Redis. Usar GET seguido de SET criaria uma race condition onde dois webhooks identicos poderiam ser processados simultaneamente.

### TTL de 24h

A Meta garante entrega at-least-once. Duplicatas geralmente chegam em poucos segundos a minutos. TTL de 24h e mais que suficiente e evita acumulo infinito no Redis.

### Verificacao de Assinatura Meta

A Meta assina cada webhook com HMAC-SHA256 usando o App Secret. Sempre verificar antes de processar:

```typescript
function verifyWebhookSignature(req) {
  const signature = req.headers['x-hub-signature-256']
  const expected = 'sha256=' + createHmac('sha256', process.env.META_APP_SECRET!)
    .update(JSON.stringify(req.body))
    .digest('hex')
  if (signature !== expected) throw new Error('Invalid webhook signature')
}
```

## Riscos

| Risco | Impacto | Mitigacao |
|-------|---------|-----------|
| Race condition entre duas instancias do Node.js processando o mesmo webhook simultaneamente | Alto | SET NX e atomico — garantido pelo Redis; documentar que e seguro em multi-instance |
| Redis indisponivel bloqueia recepcao de webhooks | Alto | Implementar fallback: se Redis down, aceitar webhook e logar alerta (degraded mode) |
| Payload muito grande gera hash diferente do esperado por serializacao inconsistente | Medio | Usar `JSON.stringify` com chaves ordenadas para garantir determinismo |
| Fila BullMQ acumula jobs nao processados em outage | Medio | Configurar `removeOnComplete` e `removeOnFail` para limitar crescimento |

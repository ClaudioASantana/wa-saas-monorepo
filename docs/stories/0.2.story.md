## User Story

**Como** arquiteto do sistema,
**Quero** que o banco de dados PostgreSQL (Supabase) tenha isolamento completo entre tenants via Row-Level Security,
**Para que** uma empresa (tenant) jamais consiga acessar dados de outra empresa, garantindo segurança e compliance.

## Escopo

### Schema Base — Tabelas Iniciais

```sql
-- Tabela de tenants (sem RLS, gerenciada pelo sistema)
CREATE TABLE tenants (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name        TEXT NOT NULL,
  slug        TEXT UNIQUE NOT NULL,
  plan        TEXT NOT NULL DEFAULT 'free',
  status      TEXT NOT NULL DEFAULT 'active',
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Exemplo: tabela de conversas (com RLS)
CREATE TABLE conversations (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id   UUID NOT NULL REFERENCES tenants(id),
  -- ... demais campos
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Indice com tenant_id primeiro (sharding-ready)
CREATE INDEX idx_conversations_tenant ON conversations(tenant_id, created_at DESC);
```

### Funcao de Contexto RLS

```sql
-- Definir contexto do tenant na sessao
CREATE OR REPLACE FUNCTION set_tenant_context(p_tenant_id UUID)
RETURNS void AS $$
BEGIN
  PERFORM set_config('app.tenant_id', p_tenant_id::text, true);
END;
$$ LANGUAGE plpgsql;
```

### Policy RLS Padrao

```sql
-- Habilitar RLS
ALTER TABLE conversations ENABLE ROW LEVEL SECURITY;

-- Policy: tenant so ve seus propios dados
CREATE POLICY tenant_isolation ON conversations
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

### Middleware Node.js

```typescript
// src/middleware/tenant.ts
export async function tenantMiddleware(req, reply) {
  const tenantId = req.headers['x-tenant-id'] // ou JWT claim
  if (!tenantId) throw new Error('tenant_id required')

  await supabase.rpc('set_tenant_context', { p_tenant_id: tenantId })
  req.tenantId = tenantId
}
```

## Dev Notes

### Importante: Service Role vs Anon Key

- **Service Role Key:** Ignora RLS — usar apenas em operacoes administrativas (criar tenant, migrations)
- **Anon/Auth Key:** Respeita RLS — usar para todas as operacoes de negocio com contexto de tenant

### Preparacao para Citus (Sharding Futuro)

Todos os indices devem ter `tenant_id` como primeira coluna. Isso permite que o Citus distribua shards por tenant sem reescrever queries.

```sql
-- Correto (sharding-ready)
CREATE INDEX idx_messages_tenant ON messages(tenant_id, created_at DESC);

-- Incorreto (evitar)
CREATE INDEX idx_messages_date ON messages(created_at DESC);
```

## Riscos

| Risco | Impacto | Mitigacao |
|-------|---------|-----------|
| Service Role Key usada onde deveria respeitar RLS (bug silencioso — todos os dados visiveis) | **Critico** | Code review obrigatorio; documentar regra: service role APENAS em operacoes admin |
| Policy RLS mal escrita permite acesso cruzado entre tenants | **Critico** | Teste automatizado de isolamento obrigatorio no DoD |
| Migration irreversivel aplicada em ambiente errado | Alto | Sempre testar migration em banco local antes de aplicar; manter rollback script |
| Citus sharding incompativel com RLS policies futuras | Medio | Consultar documentacao Citus sobre RLS antes de qualquer migracao de sharding |

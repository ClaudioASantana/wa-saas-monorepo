## User Story

**Como** desenvolvedor do backend,
**Quero** que mídias recebidas via WhatsApp sejam enviadas ao Amazon S3 de forma assincrona em background,
**Para que** o Event Loop do Node.js nunca seja bloqueado por operacoes de I/O de arquivos grandes.

---

## Acceptance Criteria

- [ ] AC-01: Cliente AWS S3 configurado com credenciais via variaveis de ambiente
- [ ] AC-02: Midia recebida no webhook e enfileirada para upload (nao processada na rota)
- [ ] AC-03: Worker BullMQ faz download da midia do servidor da Meta e upload para S3
- [ ] AC-04: URL publica (ou pre-signed) da midia salva no banco apos upload concluido
- [ ] AC-05: Registro de midia no banco com status: `pending` -> `uploaded` -> `failed`
- [ ] AC-06: Retentativa automatica em caso de falha (max 3 tentativas com backoff)
- [ ] AC-07: Midias organizadas no S3 por `{tenant_id}/{year}/{month}/{message_id}.{ext}`
- [ ] AC-08: Event Loop nao bloqueado — upload nao usa `fs.readFileSync` ou operacoes sincronas

## Escopo

### Fluxo de Upload

```
Webhook recebido (imagem/video/audio)
  └── Extrair media_id e mime_type
  └── Enfileirar job { media_id, mime_type, tenant_id, message_id }
  └── Retornar 200 imediatamente

Worker (background):
  └── Download da midia da API da Meta (URL temporaria)
  └── Stream upload direto para S3 (sem salvar disco)
  └── Atualizar banco: media_url = S3 URL
  └── Emitir evento WebSocket: 'message:media_ready'
```

### Servico de Upload S3

```typescript
// src/services/media-upload.ts
import { S3Client, PutObjectCommand } from '@aws-sdk/client-s3'
import { Readable } from 'stream'

const s3 = new S3Client({
  region: process.env.AWS_REGION!,
  credentials: {
    accessKeyId: process.env.AWS_ACCESS_KEY_ID!,
    secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY!,
  },
})

export async function uploadMediaToS3(params: {
  tenantId: string
  messageId: string
  mediaId: string
  mimeType: string
}): Promise<string> {
  // 1. Obter URL de download da Meta API
  const mediaUrl = await getMetaMediaUrl(params.mediaId)

  // 2. Stream download -> S3 (sem tocar o disco)
  const response = await fetch(mediaUrl)
  const stream = Readable.fromWeb(response.body as any)

  const ext = mimeToExtension(params.mimeType)
  const now = new Date()
  const key = [
    params.tenantId,
    now.getUTCFullYear(),
    String(now.getUTCMonth() + 1).padStart(2, '0'),
    `${params.messageId}.${ext}`,
  ].join('/')

  await s3.send(new PutObjectCommand({
    Bucket: process.env.AWS_S3_BUCKET!,
    Key: key,
    Body: stream,
    ContentType: params.mimeType,
  }))

  return `https://${process.env.AWS_S3_BUCKET}.s3.${process.env.AWS_REGION}.amazonaws.com/${key}`
}
```

### Tabela de Midias

```sql
CREATE TABLE media_files (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id   UUID NOT NULL REFERENCES tenants(id),
  message_id  UUID NOT NULL,
  media_id    TEXT NOT NULL,  -- ID da Meta
  mime_type   TEXT NOT NULL,
  s3_url      TEXT,
  status      TEXT NOT NULL DEFAULT 'pending', -- pending | uploaded | failed
  attempts    INT NOT NULL DEFAULT 0,
  error       TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_media_files_tenant ON media_files(tenant_id, created_at DESC);
```

## Dev Notes

### Stream Direto (Sem Disco)

Nunca usar `fs.writeFile` ou bufferizar a midia em memoria. Usar stream pipe diretamente:

```
Meta API response stream -> S3 PutObject stream
```

Isso garante que arquivos grandes (videos) nao explodam a memoria do servidor.

### Organizacao S3

Estrutura `{tenant_id}/{year}/{month}/{message_id}.{ext}` facilita:
- Particionamento por tenant para billing
- Lifecycle policies da AWS por data
- Isolamento logico por tenant

### Tipos de Midia Suportados

| MIME Type | Extensao | Max Size |
|-----------|----------|----------|
| `image/jpeg` | `.jpg` | 5MB |
| `image/png` | `.png` | 5MB |

| `video/mp4` | `.mp4` | 16MB |
| `audio/ogg` | `.ogg` | 16MB |

## Riscos

| Risco | Impacto | Mitigacao |
|-------|---------|-----------|
| Stream de video grande (>16MB) excedendo timeout padrao do worker BullMQ | Medio | Configurar `timeout` do job para 5 minutos; separar queue de videos da de imagens |
| URL temporaria de download da Meta expirando antes do worker processar | Alto | Processar download imediatamente apos receber o media_id (prioridade alta na fila) |
| Credenciais AWS hardcoded no codigo por acidente | **Critico** | Nunca commitar credenciais; usar IAM roles em producao; `.env` no gitignore |
| Bucket S3 publico expondo midias de outros tenants | **Critico** | Bucket PRIVADO; usar pre-signed URLs com TTL curto para acesso |
